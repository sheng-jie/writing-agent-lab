# Studio 写作工作流实例工作区模块化

Status: ready-for-agent

## Problem Statement

FlowDraft 的 `/studio` 页面已经完成从原型到 React 页面迁移，但当前路由入口同时持有写作工作流实例的页面状态、8 个步骤的元数据、流程导航、标题与通知操作、阶段操作栏、通用面板，以及全部步骤工作区的 JSX。一个步骤的工作区、其当前步骤 Agent 交互和前端工具发生变化时，维护者必须修改同一个大页面，导致改动难以定位、审阅困难，并且容易影响其他阶段。

用户需要将工作台整理为可演进的模块结构：工作台壳层只负责写作工作流的整体推进和共同状态；每个步骤工作区独立维护其编辑界面及与 Agent 的协作；已有的通用 `AgentPanel` 继续作为唯一 Agent 面板抽象，而不是再创建一个平行的 Studio 专属助手组件。

## Solution

将 `/studio` 改造成由一个 StudioWorkspace 组合的工作台。StudioWorkspace 集中管理写作工作流实例的当前步骤、标题、流程栏偏好、通知和跨步骤操作；左侧流程栏、顶部元数据与底部操作栏成为稳定的壳层模块；8 个步骤工作区分别实现并由步骤映射装配。

每个步骤工作区将自己的编辑区与 `AgentPanel` 一起组合，沿用 `/clarify` 的模式：业务步骤在工作区内挂载对应的 Copilot 工具宿主，`AgentPanel` 仅提供通用对话布局、消息、欢迎引导、输入和运行状态。不得引入 `StudioAssistant` 或重复实现聊天 UI。

## User Stories

1. As a FlowDraft 作者, I want to在一个稳定的工作台中继续推进写作工作流, so that 我在切换捕捉想法、选题生成、大纲规划和后续阶段时不会失去流程上下文。
2. As a FlowDraft 作者, I want to在每个工作区看到与当前阶段匹配的编辑界面, so that 我只处理当前阶段需要的输入、产物和行动。
3. As a FlowDraft 作者, I want to在捕捉想法工作区整理灵感和素材, so that 原始观察能够进入后续写作意图识别与选题生成。
4. As a FlowDraft 作者, I want to在选题生成工作区查看并确认选题候选, so that 我能形成明确的确定选题后再进入大纲规划。
5. As a FlowDraft 作者, I want to在大纲规划工作区维护写作大纲, so that 文章主线、章节任务和素材缺口可以清晰推进。
6. As a FlowDraft 作者, I want to在初稿工作区编辑初稿, so that 我能继续补充自己的观点、案例和表达。
7. As a FlowDraft 作者, I want to在润色改写与去 AI 味工作区分别处理可读性和作者表达, so that 润色稿保留我的判断而不是变成模板化内容。
8. As a FlowDraft 作者, I want to在文章配图工作区维护配图稿所需的配图需求, so that 图片能够解释文章，而不只是装饰文章。
9. As a FlowDraft 作者, I want to在排版发布工作区查看排版发布检查和预览, so that 我能准备文章的目标平台适配动作。
10. As a FlowDraft 作者, I want to在每个工作区使用与当前阶段相关的 Agent, so that Agent 的建议和工具不会混入不相关阶段的操作。
11. As a FlowDraft 作者, I want to保留左侧流程、当前步骤、文章标题、进度和底部推进操作, so that 页面拆分不会改变现有工作台的核心使用方式。
12. As a FlowDraft 作者, I want to收起或展开流程栏后保留我的偏好, so that 我能在不同屏幕空间下专注于工作区内容。
13. As a FlowDraft 作者, I want to在保存、复制阶段内容、推进步骤和工具执行后得到可感知反馈, so that 我知道当前操作是否已经生效。
14. As a FlowDraft 开发者, I want to只修改一个步骤工作区就能改变该阶段的内容布局, so that 不需要审阅或触碰其他七个步骤的 JSX。
15. As a FlowDraft 开发者, I want to让步骤元数据集中定义, so that 流程栏、顶部状态、进度、操作栏和步骤映射使用同一份步骤身份与文案。
16. As a FlowDraft 开发者, I want to复用现有 AgentPanel, so that Agent 对话布局、消息渲染、输入、欢迎引导和运行状态在 `/clarify` 与 `/studio` 保持一致。
17. As a FlowDraft 开发者, I want to让每个步骤在本地挂载其 Copilot 工具宿主, so that Agent 只获得当前阶段允许的工具和状态。
18. As a FlowDraft 开发者, I want to让仅供当前步骤临时使用的 UI 状态留在步骤工作区内, so that 工作台壳层不因局部表单与展示状态而膨胀。
19. As a FlowDraft 开发者, I want to仅将跨步骤复用或需要保存的状态提升到工作台控制器, so that 写作工作流实例的共同状态集中而不过度全局化。
20. As a FlowDraft 维护者, I want to保留现有视觉、响应式行为、键盘焦点和减少动效支持, so that 这次结构调整不会回归已经验证过的产品体验。
21. As a FlowDraft 维护者, I want to通过一个高层组合 seam 验证工作台行为, so that 测试关注用户可观察的工作区切换、流程操作和 Agent 挂载，而不是薄展示组件的内部结构。

## Implementation Decisions

- `/studio` 的路由入口只负责装配 StudioWorkspace 与所需的 CopilotKit 运行时上下文；路由入口不再包含写作工作流实例状态、步骤数据或步骤工作区 JSX。
- StudioWorkspace 是工作台的组合模块。它负责工作流壳层、当前步骤选择、文章标题、流程栏偏好、进度、通知、保存、复制阶段内容和推进/返回阶段等跨步骤行为。
- StudioWorkspace 的 Interface 应保持小而稳定：它向壳层模块和当前步骤工作区提供当前步骤、项目级可保存状态、步骤选择与推进动作、通知动作；它不暴露或管理每个步骤的局部展示细节。
- 建立统一的步骤身份与步骤元数据模块。步骤身份使用领域术语对应写作工作流中的捕捉想法、选题生成、大纲规划、撰写初稿、润色改写、去 AI 味、文章配图和排版发布；流程栏、顶部状态、操作栏和工作区映射从该元数据读取。
- 现有原型中的“选题澄清”在拆分时应改用领域词汇“选题生成”。“写作意图识别”仍属于捕捉想法阶段的核心活动，不与选题生成混用。
- 左侧流程栏、顶部元数据、底部操作栏、Toast 和可复用的面板/检查清单可以成为共享壳层模块。它们只接收渲染所需数据和操作回调，不直接操作 Copilot 工具或阶段领域状态。
- 不创建 StudioAssistant 模块。当前步骤的 Agent 区域属于步骤工作区的组成部分；通用 Agent 交互继续使用现有 AgentPanel。
- 每个步骤工作区是独立模块，负责组合该阶段的编辑区、阶段局部状态、阶段产物展示和对应 AgentPanel。工作区名称与步骤身份一致。
- 每个需要 Agent 协作的步骤工作区在自身内部挂载对应的 Copilot 工具宿主，组织形式参考 `/clarify`：工作区组合 AgentPanel，工具宿主通过 AgentPanel 的 children 注入。工具宿主负责 `useFrontendTool`、人机协同交互和必要的 Agent 状态同步；AgentPanel 不感知写作工作流字段。
- 工作区的 Agent 标题、描述、欢迎引导、输入提示与允许工具必须针对当前阶段定义。例如捕捉想法阶段仅暴露素材整理与写作意图识别相关工具；大纲规划阶段仅暴露写作大纲相关工具；文章配图阶段仅暴露配图稿相关工具。
- 为当前步骤选择建立一个单一映射模块，将步骤身份映射到相应工作区。该映射是工作区替换与新增阶段的唯一装配点，避免在 StudioWorkspace 中使用按索引分支的 JSX。
- 将工作台状态集中在类似 `useClarifyState` 的控制器 Hook 中。控制器处理定时 Toast 清理、流程栏偏好持久化、步骤推进、标题和跨步骤项目状态更新，并在需要时通过 `useAgentContext` 向当前 Agent 提供当前写作工作流实例和阶段状态。
- 步骤局部且不可跨步骤复用的状态保留在步骤工作区中；写作意图、确定选题、写作大纲、初稿、润色稿、配图稿等需要后续阶段读取的产物状态属于写作工作流实例的共同状态，由控制器提供受控更新动作。
- 页面现有 `studio.css` 的基础令牌、工作台网格、响应式结构、焦点样式和减少动效规则继续保留。共享壳层样式与步骤工作区样式可以按职责拆分，但不得改变产品的视觉合同。
- 本次是前端模块化，不新增持久化模型、后端接口、排版发布执行能力或新的 Agent 运行时。后端写作工作流实例持久化仍不在本需求范围内。

## Testing Decisions

- 已确认的最高测试 seam 是 StudioWorkspace。测试通过该 seam 验证用户可观察到的工作区切换、流程栏收缩、上一步/推进、标题与阶段内容复制、Toast 反馈以及当前步骤所组合的 AgentPanel 与工具宿主，而不是测试展示型子组件的实现细节。
- 一个好的测试应从作者的可见行为出发：选择写作工作流中的某阶段后出现该阶段的工作区与对应 Agent 面板；执行流程动作后当前阶段、进度与操作可见状态一致；不依赖组件树结构、CSS 类名或内部 Hook 调用次数。
- 为工作台控制器增加针对跨步骤行为的单元测试：步骤不能在首阶段再后退；推进到下一阶段会更新当前步骤和进度；最后阶段不会越界；流程栏偏好会写入并恢复本地存储；通知会在规定时限后关闭；项目级产物更新能供后续步骤读取。
- 为步骤映射增加类型或行为验证，确保每个定义的步骤身份都有恰好一个工作区实现，且不存在未经元数据定义的工作区入口。
- 为每个带 Agent 的步骤工作区增加组合测试，验证它提供阶段正确的 AgentPanel 文案和工具宿主。测试工具的用户可见结果或对控制器的结果更新，而不是断言 CopilotKit 的内部调用顺序。
- 延续 `/clarify` 的先例：AgentPanel 是既有通用 Adapter，工作区工具宿主是阶段业务 Adapter；测试应复用该模式，不创建第二套聊天面板或聊天渲染测试。
- 保留并扩展现有浏览器验证：桌面、平板和窄屏下工作台不应产生意外横向滚动；流程栏在窄屏变为可横向滚动的步骤列表；助手区域随当前工作区组合并在较窄布局下重排。
- 重构完成后运行前端生产构建和相关测试。构建成功是必要条件，但不替代 StudioWorkspace 行为测试和浏览器可视检查。

## Out of Scope

- 改变写作工作流的业务顺序、增加新的阶段，或改变各阶段当前展示的产品功能。
- 创建 StudioAssistant、StudioChat 或任何平行于 AgentPanel 的通用 Agent UI。
- 重写 AgentPanel、AgentInput、AgentMessages、useAgentChat 或 `/clarify` 的既有通用 Agent 抽象。
- 在本次重构中完整实现所有步骤的真实模型调用、工具执行、文章生成或后端持久化。
- 为每个步骤引入独立路由、独立 CopilotKit runtime 或独立 Agent 线程；步骤仍在同一 StudioWorkspace 中切换。
- 持久化写作工作流实例、中间阶段产物、排版发布任务或用户的工作区布局之外的偏好。
- 改变已完成页面迁移的视觉方向，或以模块化为理由进行无关的 UI 重设计。

## Further Notes

- 本需求的目标是提高模块的 Depth、Locality 和 Leverage，而不是将每一段 JSX 机械拆成薄组件。共享模块仅在存在真实复用或稳定 Interface 时提取；单次使用的纯展示结构可以留在所属步骤工作区内部。
- AgentPanel 已是全局通用 Agent 面板的 Interface；Studio 工作区应在它之上提供阶段业务能力，而不是包一层新的助手抽象。
- StudioWorkspace 是唯一新增的高层组合 seam。它把写作工作流实例的共同状态与当前步骤工作区连接起来；每个步骤工作区仅通过控制器提供的明确操作读写跨阶段产物。
- 当前页面的原型数据可以在模块化过程中迁移为步骤元数据与阶段默认状态，但它们不应继续作为页面路由入口内的大型常量。
