# 写作工作流阶段产物显式接受

Status: ready-for-agent

## Problem Statement

FlowDraft 当前把“生成或确认候选阶段产物”和“接受阶段产物”合并成了同一个动作。

在捕捉想法工作区中，作者点击 Agent 提供的“确认生成卡片”后，系统立即把捕捉想法阶段标记为 `accepted`、锁定左侧写作意图，并提前开启选题生成。作者随后在右侧协作区继续修正写作意图时，系统会把这次修正当成对已接受上游产物的修改，提示并清空当前及下游内容。

这不符合作者的操作预期。确认生成结构化写作意图卡片，只代表作者愿意把 Agent 当前识别结果沉淀为可继续修正的候选阶段产物，不代表作者已经接受该产物并完成当前阶段。

同样的问题适用于完整写作工作流：生成选题列表、写作大纲、初稿、润色稿或配图稿，都不应自动完成阶段。只有作者主动点击“下一步”，阅读接受影响和产物摘要，并在弹窗中确认后，系统才应固定当前草稿、把阶段标记为 `accepted` 并进入下一阶段。

作者需要在候选阶段产物生成后继续与 Agent 协作修正内容，且这些修正不能触发自动接受、内容清空或下游重置。阶段一旦被接受，则不再允许直接修改；作者只能通过明确重置整个写作工作流来重新开始。

## Solution

将“生成候选阶段产物”和“接受阶段产物”拆成两个独立的用户动作，并对六个正式阶段采用同一规则。

每个阶段先通过明确的完整产物生成动作形成候选阶段产物。候选阶段产物写入当前阶段的候选槽位，并以最新可编辑草稿作为界面展示与后续修正对象。此时阶段继续保持 `in-progress`，不会写入已接受产物，不会开启下一阶段，也不会清空任何内容。

候选阶段产物生成后，作者可以继续通过当前阶段的协作区修正草稿。捕捉想法工作区的左侧结构化写作意图卡片保持只读，右侧协作区是唯一修正入口。新生成结果按字段合并到当前草稿，未提供字段继续保留。

只有候选阶段产物已经生成且 Agent 空闲时，“下一步”才可用。作者点击“下一步”后，系统展示确认弹窗，说明阶段将被锁定并进入下一阶段，同时展示当前产物的关键摘要。作者确认后，系统以一个原子动作把当前草稿固定为已接受产物、将阶段标记为 `accepted`、开启并进入下一阶段。作者取消时不改变任何产物、状态或浏览位置。

阶段进入 `accepted` 后不可直接修改。作者需要返工时，只能点击重置并确认清理影响；重置会清空当前写作工作流全部阶段的状态与产物、当前写作意图和 Agent 对话，回到首次输入前。

## User Stories

1. As a FlowDraft 作者, I want to确认生成结构化写作意图卡片而不完成捕捉想法阶段, so that 我可以先看到完整结果再继续修正。
2. As a FlowDraft 作者, I want to在结构化写作意图卡片生成后继续与 Agent 对话, so that 我可以完善主题、读者、目的、平台、观点和内容边界。
3. As a FlowDraft 作者, I want to让右侧协作区的修正立即反映到左侧卡片, so that 我始终看到当前最新的写作意图草稿。
4. As a FlowDraft 作者, I want to让左侧结构化写作意图卡片保持只读, so that 我通过单一协作入口完成修正，不会产生两套编辑行为。
5. As a FlowDraft 作者, I want to再次确认 Agent 生成的写作意图时按字段合并内容, so that 新结果不会清空未重新提供的字段。
6. As a FlowDraft 作者, I want to在候选阶段产物修正期间保留已有内容和对话, so that 正常协作不会被误判为破坏性返工。
7. As a FlowDraft 作者, I want to在结构化写作意图卡片尚未生成时无法点击“下一步”, so that 零散字段不会被误当成完整产物。
8. As a FlowDraft 作者, I want to在 Agent 正在处理时暂时无法点击“下一步”, so that 我接受的内容不会在确认期间继续变化。
9. As a FlowDraft 作者, I want to主动点击“下一步”才发起阶段接受, so that 系统不会替我决定何时完成当前阶段。
10. As a FlowDraft 作者, I want to在接受前看到该动作会锁定当前阶段并进入下一阶段, so that 我理解确认后的影响。
11. As a FlowDraft 作者, I want to在接受写作意图前看到写作主题、目标读者和核心观点摘要, so that 我能快速核对将被固定的内容。
12. As a FlowDraft 作者, I want to取消接受弹窗而不改变任何状态, so that 我可以返回当前阶段继续修正。
13. As a FlowDraft 作者, I want to确认接受后固定弹窗所展示的当前草稿, so that 已接受产物与我的确认对象一致。
14. As a FlowDraft 作者, I want to在接受成功后自动进入下一阶段, so that 我无需再次执行导航动作。
15. As a FlowDraft 作者, I want to让流程进度只统计已接受阶段, so that 生成候选产物不会虚增完成进度。
16. As a FlowDraft 作者, I want to在候选选题生成后继续比较和修正, so that 生成选题列表不等于接受确定选题。
17. As a FlowDraft 作者, I want to在写作大纲生成后继续调整结构, so that 大纲生成不等于完成大纲规划。
18. As a FlowDraft 作者, I want to在初稿生成后继续补充正文, so that 第一版正文不会被自动视为已接受初稿。
19. As a FlowDraft 作者, I want to在润色稿生成后继续修改表达, so that Agent 的改写结果不会未经确认成为下游输入。
20. As a FlowDraft 作者, I want to在配图稿生成后继续检查正文与图片, so that 完整候选生成不等于最终接受。
21. As a FlowDraft 作者, I want to让六个阶段采用一致的接受交互, so that 我不必学习每个工作区不同的推进规则。
22. As a FlowDraft 作者, I want to在阶段 accepted 后看到产物不可修改, so that 已接受产物保持为稳定的下游输入。
23. As a FlowDraft 作者, I want to在 accepted 后只能通过重置进行返工, so that 不会出现上游已变而下游仍保留的隐性不一致。
24. As a FlowDraft 作者, I want to在重置前看到会清空整个写作工作流的明确提示, so that 我不会误删已有阶段产物和对话。
25. As a FlowDraft 作者, I want to取消重置而保留完整工作流, so that 误触不会造成内容丢失。
26. As a FlowDraft 作者, I want to确认重置后回到首次输入前, so that 我能从新的原始想法重新开始。
27. As a FlowDraft 作者, I want to在重置后不再看到旧阶段产物、写作意图或 Agent 对话, so that 新工作流不会混入旧上下文。
28. As a FlowDraft 开发者, I want to通过候选产物是否存在判断阶段是否具备接受条件, so that 任意非空草稿不会误开放“下一步”。
29. As a FlowDraft 开发者, I want to让候选产物、可编辑草稿和已接受产物承担不同职责, so that 生成、修正和接受三个行为具有清晰语义。
30. As a FlowDraft 开发者, I want to把接受阶段实现为单一原子操作, so that 产物固定、状态更新、下一阶段开启和工作区跳转不会部分成功。
31. As a FlowDraft 开发者, I want to从 Agent 面板获得可靠的运行状态, so that 操作栏能在内容仍变化时禁止接受。
32. As a FlowDraft 维护者, I want to通过工作流状态控制器验证完整行为, so that 测试关注作者动作产生的结果，而非 CopilotKit 或组件内部实现。

## Implementation Decisions

- 六个正式阶段统一采用“生成候选阶段产物 → 持续修正草稿 → 下一步确认接受”的推进规则。任何工作区专属的生成或确认卡片动作都不得直接把阶段标记为 `accepted`。
- 阶段状态继续只使用 `pending`、`in-progress` 和 `accepted`。不新增 `ready-for-review`、`stale`、`locked` 或其他状态；候选阶段产物是否存在用于表达当前阶段是否已经形成完整、可接受的结果。
- 复用阶段记录中的候选产物槽位表达“完整产物已生成”。候选产物生成动作同时建立候选产物和当前可编辑草稿，但阶段保持 `in-progress`。
- 零散字段更新只修改草稿，不自动创建候选阶段产物。各阶段必须通过明确的完整产物生成事件建立候选产物，之后才可能开放“下一步”。
- 候选阶段产物建立后，后续修正继续更新草稿，而不清除候选存在标记。作者无需在每次局部修改后重新生成候选产物。
- 捕捉想法阶段的 Agent 确认卡片只负责把结构化写作意图沉淀为候选阶段产物和草稿。它不写入已接受产物、不改变当前阶段、不打开选题生成，也不触发 Agent 对话重置。
- 捕捉想法阶段再次生成卡片时，按字段合并新内容到当前草稿。新结果未提供的字段保持原值；不得整体清空当前写作意图。
- 捕捉想法工作区左侧卡片是当前写作意图草稿的只读投影。右侧协作区及其业务工具是 accepted 前修正写作意图的唯一入口。
- 通用阶段动作只在候选阶段产物存在且 Agent 空闲时返回可推进状态。仅有任意非空草稿或更新时间不再足以开放“下一步”。
- 通用 Agent 面板需要向所属工作区或工作流控制器暴露只读运行状态。该能力只服务于接受条件与交互禁用，不允许工作流控制器操作 CopilotKit 内部运行细节。
- 点击“下一步”不立即修改工作流，而是创建待确认动作并打开弹窗。弹窗说明确认后当前阶段将锁定并进入下一阶段，并展示当前产物的关键摘要。
- 捕捉想法阶段的摘要至少包含写作主题、目标读者和核心观点。其他阶段提供与本阶段产物相匹配的简短摘要，不在弹窗内重复渲染完整产物。
- 用户确认接受时，以单一状态转换固定当前草稿为已接受产物、将当前阶段设为 `accepted`、递增阶段修订号、将下一阶段从 `pending` 改为 `in-progress`，并把真实当前阶段和浏览工作区切换到下一阶段。
- 用户取消接受时，候选产物、草稿、已接受产物、阶段状态、修订号、真实当前阶段和浏览工作区均保持不变。
- 已接受产物是后续阶段唯一稳定输入。阶段进入 `accepted` 后，项目字段更新、阶段草稿更新和 Agent 工具更新均不得修改该阶段产物。
- accepted 后不提供“重新打开阶段”或“确认修改上游并保留下游”的路径。唯一返工入口是重置当前写作工作流。
- 重置在任何 accepted 阶段触发时都必须弹窗确认，不以是否已有下游产物决定是否跳过确认。提示明确说明将清空整个写作工作流，而不只清空当前及后续阶段。
- 确认重置后，所有阶段恢复初始状态，当前写作意图和其他项目阶段产物清空，文章保存标记清除，浏览工作区回到捕捉想法，并清空 Agent 对话。
- 本需求不改变写作工作流的六阶段顺序，也不把写作意图、初稿、润色稿或配图稿拆成独立领域模型。
- 本规格取代既有工作流状态规格中以下决策：引入三种状态以外的阶段状态；允许重新打开 accepted 阶段；上游修改后保留下游并标记失效；通过任意非空草稿开放推进。既有的六阶段顺序、阶段记录、工作流控制器、候选/草稿/已接受产物分离和按 accepted 计算进度继续保留。

## Testing Decisions

- 已确认的唯一主要测试 seam 是工作流状态控制器。测试通过作者可执行的高层动作输入，包括生成候选阶段产物、修正草稿、点击下一步、确认、取消和重置，并断言工作流快照、项目产物、当前工作区和可观察通知。
- 一个好的测试只验证外部行为：按钮是否可用、弹窗是否出现、确认或取消后阶段是否推进、已接受产物是否等于确认时草稿、重置后内容是否消失。测试不得依赖内部 Hook 调用次数、React 组件层级、CSS 类名、CopilotKit 消息实现或状态更新函数数量。
- 扩展现有写作工作流 Vitest 测试作为先例，覆盖候选产物不存在时不可推进、候选产物存在时可推进、任意非空草稿不足以推进，以及 accepted 进度计算保持不变。
- 为工作流状态控制器增加行为测试，覆盖卡片生成后阶段仍为 `in-progress`、候选与草稿已建立、下一阶段仍为 `pending`、后续字段修正不清空内容且不改变状态。
- 为接受动作增加行为测试，覆盖点击下一步只打开确认、取消完全无副作用、确认后原子写入 accepted 并进入下一阶段，以及接受快照与弹窗摘要来源一致。
- 为六个正式阶段使用参数化测试验证相同的接受规则，避免只修复捕捉想法而让其他阶段继续自动接受。
- 为 Agent 运行状态增加控制器或组合层测试：候选产物存在但 Agent 运行时下一步不可用；Agent 空闲后恢复可用。不测试 CopilotKit 自身如何计算运行状态。
- 为 accepted 后保护增加行为测试，验证项目字段更新、阶段草稿更新和 Agent 工具更新均不能修改已接受阶段。
- 为重置增加行为测试，覆盖 accepted 后始终要求确认、取消无副作用，以及确认后清空所有阶段状态与产物、项目内容、文章保存标记和 Agent 对话并回到捕捉想法。
- UI 只补充少量用户可观察行为测试：没有候选时“下一步”禁用；Agent 运行时禁用；点击后弹窗展示影响与摘要；确认和取消调用相应的控制器动作。UI 测试不重复状态控制器的完整转换矩阵。
- 完成后运行前端 Vitest 相关测试、前端 lint 和生产构建。浏览器验证覆盖捕捉想法的真实交互：生成卡片后可继续对话修改；内容不被清空；下一步确认后才进入选题生成；accepted 后只能重置。

## Out of Scope

- 改变六个正式阶段的顺序、增删阶段或重新定义产物链路。
- 实现后端持久化、工作流 HTTP 合同、并发修订冲突或跨设备恢复。
- 改变 Agent 的写作质量、提示词策略、联网搜索能力或模型选择。
- 为左侧结构化写作意图卡片增加直接编辑表单。
- accepted 后提供局部重新打开、保留下游的上游修改、失效标记或内容合并流程。
- 增加撤销栈、阶段版本历史、分支工作流或多个候选版本比较。
- 重写通用 Agent 对话 UI、消息渲染或 CopilotKit 运行时。
- 对 Studio 进行与接受流程无关的视觉重设计。
- 实现文章保存后的排版发布能力。

## Further Notes

- 本规格采用领域词汇中的“候选阶段产物”“接受阶段产物”和三种“阶段状态”。界面上的“确认生成卡片”是候选产物生成动作，不是阶段接受动作。
- `proposal` 可作为候选阶段产物的内部实现名，但不应在用户界面文案中出现。
- 接受确认弹窗必须基于稳定草稿。通过“Agent 空闲才允许打开弹窗”消除弹窗打开后草稿继续变化的问题，不需要引入额外快照版本或并发协议。
- 现有工作流状态控制器已经集中处理阶段推进、重置和项目清理，是本需求最小且最高的行为 seam。实现应在该模块收紧规则，避免把状态转换散落到六个工作区。
- 该规则有意选择严格一致性：accepted 代表不可变的稳定下游输入。返工成本通过彻底重置显式呈现，而不是保留可能与上游不一致的下游产物。
