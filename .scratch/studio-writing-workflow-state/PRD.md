# Studio 写作工作流状态与产物链路

Status: ready-for-agent

## Problem Statement

FlowDraft 的 `/studio` 已完成工作区组件拆分，但目前仍是一个可自由切换的页面原型，而不是可持续推进的写作工作流实例。

作者在工作台中会遇到以下问题：

- 左侧流程的“已完成”仅由当前浏览位置推断。只要点击后续工作区，前序阶段就会显示完成，即使写作意图、确定选题或写作大纲尚未确认。
- 当前浏览的工作区、工作流实际阶段、阶段产物和 Toast/侧栏收起等界面状态被混在同一个前端状态中，无法可靠表达“正在编辑”“待确认”“已确认”“需要重新检查”等差异。
- 阶段产物同时散落在项目字段和通用字典中。Agent 更新通用字段时，不一定会更新后续阶段真正读取的产物，导致产物链路断裂。
- “确认选题”“采用写作大纲”等按钮实际上调用同一个按数组跳转的推进动作，没有准入条件，也没有真正确认产物。
- 修改已确认的上游产物时，下游产物不会被标记为需要检查，作者可能在不知情的情况下继续使用基于旧选题或旧大纲生成的内容。
- “已自动保存”、进度、检查项和阶段质量指标目前主要是静态演示数据，无法反映真实工作流状态。
- 后端已有最小的写作工作流实例，但它不持久化、没有身份、没有工作流用例或 HTTP 合同，且无法表达阶段草稿、待确认产物和已确认产物。

作者需要一个以写作工作流实例为中心的 Studio：每个阶段的产物都有明确状态；作者明确确认后才成为下游输入；Agent 只提出可审阅建议；上游变动能够告知作者对下游内容的影响；刷新后仍能回到同一次创作过程。

`/clarify` 页面不属于本需求的业务流程、状态来源或路由设计。它只可作为通用 Agent 面板与前端工具宿主的实现参考。

## Solution

将 Studio 改造为以一份可持久化的写作工作流实例为唯一事实来源的工作台。

写作工作流只保留六个正式阶段：捕捉想法、选题生成、大纲规划、撰写初稿、润色改写、文章配图。去 AI 味作为润色改写中的处理能力；排版发布发生在定稿保存为文章后，不再作为写作工作流阶段。

每个阶段维护草稿、待确认产物、已确认产物、修订号和状态。只有已确认产物可以作为后续阶段输入。作者通过明确的阶段动作提交审阅、确认、重新打开或处理失效内容；系统不再通过页面索引自动推进。

Studio 前端通过一个高层工作流控制器读取和更新工作流快照，并将当前浏览位置、流程栏偏好、Toast 等界面状态与领域状态分离。后端通过写作工作流 HTTP 合同提供创建、读取、保存阶段草稿、提交审阅、确认阶段、重新打开阶段和定稿保存为文章等能力。

作者确认配图稿后，系统形成定稿并创建文章；之后才进入独立的排版发布体验。

## User Stories

1. As a FlowDraft 作者, I want to开始一份新的写作工作流实例, so that 我的一次创作过程有可恢复的身份和连续状态。
2. As a FlowDraft 作者, I want to在 Studio 中看到捕捉想法、选题生成、大纲规划、撰写初稿、润色改写和文章配图六个正式阶段, so that 我知道文章正沿着一致的写作工作流推进。
3. As a FlowDraft 作者, I want to在捕捉想法阶段整理原始灵感和素材并确认写作意图, so that 后续选题生成有明确的输入。
4. As a FlowDraft 作者, I want to在选题生成阶段查看选题列表、选择并确认一个确定选题, so that 后续工作都围绕同一个写作方向展开。
5. As a FlowDraft 作者, I want to在大纲规划阶段编辑并确认写作大纲, so that 初稿撰写有清晰的文章主线、章节任务和素材缺口。
6. As a FlowDraft 作者, I want to在撰写初稿阶段持续编辑初稿, so that 我可以把自己的判断、案例和表达补充进文章。
7. As a FlowDraft 作者, I want to在润色改写阶段处理表达、节奏和去 AI 味问题, so that 润色稿既可读又保留我的个人判断。
8. As a FlowDraft 作者, I want to在文章配图阶段维护配图稿, so that 图片能解释内容而不只是装饰文章。
9. As a FlowDraft 作者, I want to明确确认每个阶段的产物, so that 我知道哪一版内容会成为后续阶段的输入。
10. As a FlowDraft 作者, I want to在尚未满足前置条件时看到不能推进的原因, so that 我不会误以为仅切换页面就完成了一个阶段。
11. As a FlowDraft 作者, I want to回看已经确认的阶段, so that 我能复查之前的判断而不改变工作流实际阶段。
12. As a FlowDraft 作者, I want to重新打开一个已确认阶段继续编辑, so that 我可以修正前面的判断而不是被流程锁死。
13. As a FlowDraft 作者, I want to在修改已确认写作意图、确定选题或写作大纲后看到下游影响, so that 我知道哪些产物基于旧内容，需要重新检查。
14. As a FlowDraft 作者, I want to保留需要重新检查的下游产物, so that 我能决定保留并手动修改、基于新输入重新生成，或放弃上游变更，而不是丢失已有工作。
15. As a FlowDraft 作者, I want to刷新或重新进入同一 Studio 时恢复写作工作流实例, so that 创作不会因页面关闭而丢失。
16. As a FlowDraft 作者, I want to看到真实的保存状态、确认状态、流程进度和待处理提示, so that 我能判断文章是否真的已被保存和可以推进。
17. As a FlowDraft 作者, I want to让左侧流程栏显示等待前一步、进行中、待确认、已确认、需补充或需检查等状态, so that 进度反映真实产物状态而不是点击顺序。
18. As a FlowDraft 作者, I want to在当前阶段看到只与该阶段相关的 Agent 建议, so that Agent 不会混入无关的写作操作。
19. As a FlowDraft 作者, I want to先审阅并采用 Agent 给出的候选产物或局部补丁, so that Agent 不会未经我确认覆盖文章内容或推进工作流。
20. As a FlowDraft 作者, I want to在确认配图稿后形成定稿并保存为文章, so that 完成的内容成为可持续管理的作品。
21. As a FlowDraft 作者, I want to只在文章保存后进入排版发布, so that 平台适配不会干扰文章形成前的写作工作流。
22. As a FlowDraft 开发者, I want to区分当前浏览的工作区和写作工作流的当前阶段, so that 回看、编辑和流程推进不会相互误判。
23. As a FlowDraft 开发者, I want to通过类型化阶段产物表达草稿、待确认产物和已确认产物, so that 后续工作区不会依赖无语义的字符串字段或通用字典。
24. As a FlowDraft 开发者, I want to通过一组明确的阶段命令确认、重新打开和处理产物, so that “下一步”不再隐藏业务规则。
25. As a FlowDraft 开发者, I want to让 Agent 只提出阶段相关的候选产物或补丁, so that 业务工具保有明确语义，作者保持最终控制权。
26. As a FlowDraft 开发者, I want to将保存、确认、失效传播和错误恢复集中在一个工作流控制模块中, so that 各阶段工作区不再复制流程规则。
27. As a FlowDraft 后端维护者, I want to持久化写作工作流实例及其阶段状态, so that Studio 可以恢复一次未完成的创作过程。
28. As a FlowDraft 后端维护者, I want to保留阶段产物作为写作工作流实例内部状态而非独立领域模型, so that 领域模型符合产物链路的定义。
29. As a FlowDraft 后端维护者, I want to只在定稿保存后创建文章, so that 文章保持为可发布内容作品，而不是中间阶段的别名。
30. As a FlowDraft 维护者, I want to通过公共写作工作流 HTTP 合同验证主要行为, so that 测试覆盖真实的流程结果而非组件或数据库实现细节。

## Implementation Decisions

- 写作工作流的正式阶段固定为：捕捉想法、选题生成、大纲规划、撰写初稿、润色改写、文章配图。现有“去 AI 味”不再是独立阶段，而是润色改写阶段的处理能力；现有“排版发布”从写作工作流导航中移除，改为文章保存后的独立后续动作。
- 写作工作流实例是一次创作过程的中心领域对象。写作意图、选题列表、确定选题、写作大纲、初稿、润色稿和配图稿是其内部阶段产物，不引入这些产物各自的聚合根或仓储。
- 每个正式阶段使用统一的阶段记录表达其状态和版本。阶段记录至少包含：阶段状态、作者正在编辑的草稿、待作者审阅的候选产物、已确认产物、修订号、更新时间，以及用于判断下游是否基于旧输入的上游修订信息。
- 阶段状态使用以下稳定语义：`locked` 表示缺少前置已确认产物；`in-progress` 表示可以编辑；`ready-for-review` 表示已有可确认产物；`accepted` 表示产物已确认并可供下游使用；`needs-revision` 表示当前阶段缺少必要内容；`stale` 表示当前产物依赖的上游已发生变化，必须由作者处理。
- 写作工作流实例记录真实的当前阶段；Studio 界面单独记录当前浏览的工作区。作者可以浏览和重新打开已确认阶段，但浏览行为不得改变真实当前阶段、确认状态或整体进度。
- 下游阶段只读取上游已确认产物，不读取上游未确认草稿或 Agent 候选产物。
- 推进流程不再使用通用的按数组顺序跳转操作。工作流公开的高层 Interface 是：创建工作流、读取工作流、保存阶段草稿、提交阶段审阅、确认阶段产物、重新打开阶段、处理失效产物，以及确认定稿并保存为文章。每个命令在其内部校验前置条件和状态转换。
- 修改已确认产物时，系统递增该阶段修订号，并将依赖旧修订的下游阶段标记为 `stale`。系统保留下游内容，不静默删除或覆盖；作者可选择保留并手动检查、基于新输入重新生成，或取消上游变更。
- 流程进度仅由已确认的正式阶段计算，不由当前浏览位置计算：已确认阶段数除以正式阶段总数。流程栏状态也由阶段记录推导，不能再通过步骤索引判断“已完成”。
- 顶部保存提示、阶段检查项、字数、进度和质量提醒必须来自真实保存结果、已确认产物和派生检查结果。演示性固定文字和固定分数不得继续充当真实状态。
- 前端建立一个深模块作为工作流控制器。它向工作区和壳层提供小而稳定的 Interface：读取工作流快照、打开工作区、编辑阶段草稿、提交审阅、确认阶段、重新打开阶段、采用或忽略 Agent 候选产物，以及处理界面通知。保存、并发错误、失效传播和恢复逻辑集中在该模块内。
- Studio 壳层、流程栏、顶部栏和底部操作栏仅根据工作流快照和可执行动作渲染。各阶段工作区只编辑自己的阶段草稿和展示自己的阶段产物，不直接修改其他阶段或推断整体流程。
- 每阶段 Agent 通过当前阶段的业务工具宿主与工作流控制器集成。工具使用明确业务语义，例如提出选题候选、提出写作大纲、提出初稿补丁、提出改写建议、识别模板化表达或提出配图稿建议；不再使用任意 `field`/`value` 写入工具。
- Agent 的结果写入待确认产物或局部候选补丁。作者可采用全部、采用局部、继续修改或忽略。Agent 不得直接确认阶段、覆盖已确认产物或绕过作者推进写作工作流。
- 写作工作流实例需要持久化适配器、应用用例和 HTTP 合同。公共合同提供创建和读取工作流，以及对指定阶段保存草稿、提交审阅、确认、重新打开和处理失效内容的操作。该合同是跨前后端的主要行为 seam。
- 定稿不是独立阶段产物记录。作者确认配图稿后，应用用例从已确认配图稿形成定稿并创建文章；返回文章身份后，前端转入排版发布体验。
- Studio 路由采用新建工作流与按工作流身份恢复工作流的形式。排版发布使用文章身份而非工作流阶段身份。
- `/clarify` 不读取、写入或创建 Studio 的写作工作流实例；不迁移其状态、路由或业务工具。本需求仅可沿用它已存在的通用 Agent 面板与工具宿主组织方式。
- 此需求取代此前“Studio 写作工作流实例工作区模块化”PRD 中将去 AI 味和排版发布视为独立 Studio 步骤、以及仅前端模块化且不持久化工作流的决策。已完成的通用 AgentPanel 与步骤工作区拆分仍可保留为实现基础。

## Testing Decisions

- 已确定的最高行为 seam 是写作工作流 HTTP 合同。测试从创建写作工作流实例、保存阶段草稿、提交审阅、确认阶段、修改上游产物、处理失效内容和定稿保存文章等公共行为验证结果，而不测试 EF Core 调用、状态容器实现、React 组件树或 Agent SDK 调用细节。
- 一个好的测试只断言作者或调用方可观察到的结果：阶段是否可确认、当前阶段是否推进、下游是否标记为需检查、已确认产物是否成为下游输入、文章是否只能从定稿创建，以及刷新后是否能返回相同的工作流快照。
- 领域测试覆盖写作工作流实例的转换规则：不能确认错误阶段或缺失前置条件的产物；确认阶段后会推进；重新打开已确认阶段会影响正确的下游阶段；变更上游已确认产物会保留但标记正确的下游产物；工作流完成后不再接受阶段确认。
- 应用测试通过写作工作流仓储端口验证创建、加载、保存草稿、提交审阅、确认、重新打开、失效处理和定稿保存文章用例的可观察结果。测试使用轻量内存适配器，不依赖数据库交互次数。
- 基础设施集成测试使用隔离 SQLite 存储验证写作工作流实例及其阶段记录能够被保存和重新加载，且修订、状态、草稿、待确认产物、已确认产物和失效信息保持完整。
- API 集成测试验证写作工作流 HTTP 合同的状态码和响应快照；尤其覆盖非法阶段转换、过期修订或并发保存冲突，以及定稿创建文章后的结果。
- 前端在工作流控制器 seam 增加行为测试：当前浏览工作区不改变真实当前阶段；流程栏状态和进度仅由已确认阶段派生；阶段的可执行操作与阶段状态一致；失效提示和作者选择会调用对应的工作流命令。测试不得依赖 CSS 类、内部 Hook 调用次数或展示组件层级。
- 前端工作区组合测试验证每个工作区仅显示本阶段的编辑面与 Agent 能力，并且 Agent 候选必须经作者采用后才修改阶段草稿或待确认产物。通用 AgentPanel 不在本需求中重写其独立测试。
- 既有后端先例使用 xUnit 与 FluentAssertions：写作工作流领域测试位于现有 WritingWorkflows 测试区域，文章领域测试位于 Articles 测试区域。新增测试应扩展同一风格。
- 现有前端尚无测试先例。新增测试应优先覆盖工作流控制器和用户可观察行为，避免为薄展示模块建立仅验证实现细节的测试。
- 完成后运行后端测试、前端相关测试和前端生产构建；并进行桌面与窄屏浏览器验证，确保流程栏、阶段状态提示、候选产物审阅区和 Agent 区域不会产生意外横向滚动或遮挡。

## Out of Scope

- `/clarify` 的路由、业务状态、写作意图识别流程或 Agent 行为改造。
- 多作者实时协作、评论、权限、团队空间或审批流程。
- 完整的文章版本历史、撤销栈、事件溯源、领域事件投递、消息代理、Saga 或 Outbox。
- 为每个阶段实现完整的模型生成质量、联网检索、图像生成或平台发布执行；本需求只规定这些能力如何进入候选产物和阶段确认链路。
- 文章的编辑、删除、归档、发布排期或平台发布接口本身。排版发布体验只在文章保存后作为后续路由/入口建立，不在本需求中实现具体平台交付。
- 重写通用 AgentPanel、AgentInput、AgentMessages 或 `/clarify` 已有的通用 Agent 抽象。
- 改变 FlowDraft 的视觉系统或进行与阶段状态、候选审阅、失效提示无关的 UI 重设计。
- 将阶段产物拆为独立聚合根、独立仓储或独立持久化业务对象。

## Further Notes

- 该方案使用 `CONTEXT.md` 的领域词汇：写作工作流实例承载一次创作过程；产物链路说明阶段产物的推进关系；文章是定稿保存后的独立可发布内容作品；排版发布不是文章形成前的必经阶段。
- 建议先完成“捕捉想法 → 选题生成 → 大纲规划”的最小持久化闭环，再扩展初稿、润色改写和文章配图。最小闭环必须验证恢复、确认、上游变更导致下游失效和重新检查。
- 前端工作流控制器与后端写作工作流 HTTP 合同是本需求的关键模块和主要测试 seam。它们应提供小 Interface，将复杂的保存、状态转换和失效传播集中，给步骤工作区提供更高的 Depth、Locality 和 Leverage。
- 为避免并发覆盖，工作流快照和写入命令应包含修订信息。服务端拒绝基于过期修订的写入时，前端应提示作者刷新、合并或重新应用其草稿。
- 此 PRD 记录的“最高测试 seam 为写作工作流 HTTP 合同”是当前设计假设；实现开始前应由维护者确认该 seam 也适合前后端联调与测试成本。若不适合，唯一可替代 seam 应是前端工作流控制器对工作流仓储适配器的 Interface，而不是扩散多个低层测试 seam。
